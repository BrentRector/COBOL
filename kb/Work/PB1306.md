## Measured

### Finding varying-clause — ISO §13.18.64.3 SR2, SR3; §13.18.64.4 GR1, GR3, GR4 (rejects-legal-source; rows GR-13.18.64.4-1, GR-13.18.64.4-3, GR-13.18.64.4-4, SR-13.18.64.3-2, SR-13.18.64.3-3)

**Mechanism.** F2 - VARYING counters are modelled only on the PRINTABLE (leaf) entry: DataBinder.Reports collects `varyings` per entry but attaches them only via field.Varyings on a ReportFieldModel, and resolves a counter only against the entry's own list, so a group entry's VARYING is silently discarded, a subordinate entry cannot reference an ancestor's counter, and nesting-based rules cannot see ancestor counters.

**Repro.** 01 DET-A TYPE DE. 02 LINE PLUS 1. 03 OCCURS 3 TIMES STEP 5 VARYING K FROM 1 BY 1. 04 COLUMN 1 PIC 9 SOURCE K.  (probe vgrp); and 03 OCCURS 2 TIMES STEP 10 VARYING J FROM 1. 04 COLUMN 1 PIC 99 OCCURS 2 TIMES STEP 3 VARYING K FROM J * 10 + 1 SOURCE K. (probe vsr3sub)

**Expected, from the standard.** GR1 'Each entry containing a VARYING clause establishes an independent temporary integer data item'; SR2 'This definition of data-name-1 may be referenced only within the current entry or a subordinate entry'; SR3 permits it in a subordinate entry's FROM/BY. vgrp prints `1    2    3`; vsr3sub compiles and prints the subordinate counters starting at 11 and 21. SR2 must reject `VARYING K` reused in a subordinate of an entry whose VARYING already defines K (probe vsr2sub).

**Observed.** vgrp: error COBOLNET0899: RD 'R-V': SOURCE 'K' does not resolve to a data item; vsr3sub: error COBOLNET1639 'J' is not defined; vsr2sub compiles clean and prints `1  2      3  4`.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs lines ~1597-1660 (varyings capture), ~1935-1954 (FieldVaryingSource resolution / field.Varyings.AddRange), ~2664-2672 (SR2 loop over fields only); the `chain` tuple carries no counters

### Finding varying-clause — ISO §13.18.64.3 SR3; §13.18.64.4 GR3 b) (rejects-legal-source; rows SR-13.18.64.3-3, GR-13.18.64.4-3)

**Mechanism.** F3 - the SR3-permitted reference to a counter inside arithmetic-expression-2 of the same clause is staged loud (ReportVaryingCounterInExpression, COBOLNET0899) because FROM/BY expressions are bound by ReportWriterBinder through ordinary data-name resolution, which has no scope for compose-local VARYING counters (the same missing scope produces the cascading COBOLNET1639 'not defined').

**Repro.** 02 LINE PLUS 1. 03 COLUMN 1 PIC 9 OCCURS 3 TIMES STEP 3 VARYING K FROM 1 BY K SOURCE K. (probe vby)

**Expected, from the standard.** SR3 'may be referenced in arithmetic-expression-2 of the same VARYING clause'; GR3 a)/b): K = 1, then 1+1 = 2, then 2+2 = 4 -> `1  2  4`. Note the closed form FROM + n*BY used by EmitFieldPlacements is NOT equal to GR3b when BY depends on the counter - the fix needs a running accumulator (or a recurrence) across repetitions, including OCCURS replays.

**Observed.** error COBOLNET0899: RD 'R-V' VARYING 'K': a VARYING counter referenced inside the BY expression (ISO §13.18.64.3 SR3) is not yet implemented; error COBOLNET1639: 'K' is not defined

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs lines ~1763-1766; src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ReportWriterBinder.cs (FROM/BY bind ~line 58); src/Cobol.Net.Editions/Diagnostics/DiagnosticCatalog.cs ReportVaryingCounterInExpression

### Finding varying-clause — ISO §13.18.64.3 SR2 (under-rejects; rows SR-13.18.64.3-2)

**Mechanism.** F6 - the SR2 'defined elsewhere' screen compares each counter name only against the data-name map (ByName); it never compares VARYING names against one another, so a duplicate data-name-1 within one clause (and, with F2, within a subordinate entry) is accepted.

**Repro.** 03 COLUMN 1 PIC 9 OCCURS 3 TIMES STEP 3 VARYING K FROM 1 K FROM 2 SOURCE K. (probe vsr2dup)

**Observed.** compiles clean, runs, prints `1  2  3` (first definition silently wins).

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs lines ~2664-2672

### Finding — `qualification` (rejects-legal-source; rows `SR-8.4.2.2.1-3`)

**Mechanism.** A VARYING counter is scoped to the declaring entry alone. The per-entry `varyings` list and the FieldVaryingSource match look only at the entry's own VARYING clause. A subordinate entry's unqualified reference to the counter is legal: it is unique in the VARYING context, and §13.18.64.3 SR2 says the definition 'may be referenced only within the current entry or a subordinate entry'. The compiler rejects it as an unresolvable SOURCE operand.

**Repro.** probe/qual/c2.cob (--std 2002 and 2023): RD R-RE ... 01 DET-A TYPE DE. 02 LINE PLUS 1. 03 OCCURS 2 TIMES STEP 10 VARYING K FROM 1 BY 1. 04 COLUMN 1 PIC 9 SOURCE K. Observed: error COBOLNET0899 "RD 'R-RE': SOURCE 'K' does not resolve to a data item (ISO §13.18.53.3 SR4)".

**Expected from the spec.** Compiles and GENERATE DET-A prints one line with 1 in column 1 and 2 in column 11. §8.4.2.2.1 rule 3 (--check OK): qualification is not required when the name "is unique within the context of a VARYING clause". §13.18.64.3 SR2 (--check OK): "This definition of data-name-1 may be referenced only within the current entry or a subordinate entry". §13.18.64.4 GR3 sets 1 for the first occurrence and adds BY 1 for the second. The §13.18.64.4 GR4 NOTE (--check OK) names the use "as a source data item". §13.18.38.4 GR12b places the second repetition 10 columns to the right.

**Observed / reasoning.** Measured with the pinned cobol.exe. Reusing the name across NON-subordinate entries works (c1 prints `2  5  8` / `1  2  3`), so only the subordinate-scope half fails. The failure is a mis-reported rejection: the 'does not resolve' message cites SOURCE SR4 for a name the VARYING clause defined. PB565 and PB215 (both landed) do not own this; no open note does. The subscript use (SOURCE WS-E(K)) hits a separate staged-loud 'subscripted SOURCE operand' stage and is not this mechanism.

**Code site.** src/Cobol.Net.Compiler/Binding/DataBinder.Reports.cs (`var varyings = new List<ReportVaryingModel>()` per entry ~line 1634; the FieldVaryingSource own-entry match ~line 1994-1999; the SOURCE resolution error ~line 2678)

## Landed 2026-10-03 (wave-1009 implementer A)

Re-probed on a fresh Debug build: vgrp (COBOLNET0899 'SOURCE K does not resolve'), vsr3sub (COBOLNET1639 'J' is not defined), vby (COBOLNET0899 + 1639), vsr2sub (compiled and printed `3  4      5  6`), vsr2dup (compiled, printed `1  2  3`) all reproduced.

**Fix (the root, not four patches).** A VARYING counter is the data item of its ENTRY (GR1), no longer a list hung on the printable leaf. `DataBinder.VaryingCountersOf` makes one `ReportVaryingModel` per written entry per enclosing occurrence (so GR3's "first occurrence" restarts inside each occurrence of an enclosing repeating entry), `BindReportEntries` keeps the scope stack `ReportGroupBuild.Varying` around the entry's replay, and each printable field snapshots the counters in scope as `ReportVaryingUse`s. A counter NAME is read through `ReferenceResolver.VaryingScope` (set by `ReportWriterBinder` for one entry's clause binding): `VaryingExpr` for the operand and expression binders, `ResolveSubscriptName` for a subscript. So a group entry's counter exists, a subordinate entry names it in SOURCE, a subscript, FROM and BY (SR2/SR3), and a BY naming a counter of its own entry binds. The emitter declares the counters in scope per placement (`EmitVaryingCounters`): the closed form FROM + n x BY, and the step-by-step recurrence only for a `Recurrent` entry (GR3 b with SR3's BY). SR1/SR2/SR3 are asked ONCE per written entry by `ScreenReportVaryingClauses` (they used to run inside the per-replay bind), SR2's arm over data items and report section names in `ResolveReports` from `ReportModel.VaryingNames`. `COBOLNET0899 report-varying-counter-in-expression` is retired.

**Spec (cite.py --check OK).** 13.18.64.3 SR2 (twice), SR3; 13.18.64.4 GR1, GR3, GR4 NOTE; 8.4.2.2.1 rule 3.

**Determination.** The standard does not order GR3 b's additions among the several counters of one entry: clause order, each BY against the counters as the previous addition left them (CONFORMANCE.md section 3 "VARYING counters of one clause").

**Goldens.** `conformance:2002/pb1306_varying_scope` (group counter, subordinate FROM naming the enclosing counter with the restart per occurrence, BY naming its own counter, sibling reuse), `conformance:negative/pb1306-varying-name-reused-in-subordinate`, `...-defined-twice-in-entry`, `...-counter-referenced-outside-its-entry`, `...-from-names-its-own-counter`. Drift test `ReportRepeatingEntryDriftTests.TheVaryingCounter_IsClosedFormOverTheOccurrenceNumber` replaces the closed-form-over-RepetitionOrdinal pin.

**Rows.** GR-13.18.64.4-1, -3, -4, SR-13.18.64.3-2, -3 and SR-8.4.2.2.1-3 CONFORMS (batch w1009a-report-binder). Sibling sweep: the same two-arm shape (a name resolved only on one binding path) was the SOURCE identifier arm, fixed by PB1292 in the same change.
