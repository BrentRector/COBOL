**Repro.** --std 2023: 01 A PIC 1(4) VALUE B"1100". 01 F1 PIC 1 VALUE B"1". IF A B-SHIFT-L 1 = B"1000" DISPLAY "Y" ELSE DISPLAY "N". IF F1 B-SHIFT-L 1 DISPLAY "Y" ELSE DISPLAY "N". **Expected from the spec.** §8.8.4.2.2 Format 2 (boolean relation) takes boolean-expression-1/-2, and §8.8.2 lists 'a boolean expression and an integer operand separated by a boolean shift operator' as a boolean expression; rule 8 gives A B-SHIFT-L 1 = 1000, so the relation is true -> Y. §8.8.4.3 SR1 is met (F1 is length 1); F1 B-SHIFT-L 1 = 0, so GR1 makes the condition false -> N. EVALUATE -> EV-Y.

**Observed / reasoning.** Relation: COBOLNET2362 'comparison operand was refused without a diagnostic ... internal error'. Simple condition: COBOLNET2318 'used as a condition, but it is a literal ...'. EVALUATE: COBOLNET2318 + COBOLNET1634. The parse-side predicate boolExprAhead (CobolParserCoreBase.cs) and boolArgAhead DO list B_SHIFT_L/R/LC/RC, and VersionConformancePass keeps a separate HasShiftOp - two arms of one dispatch, one updated when shifts landed. **Mechanism.** ConditionBinder.HasBoolOp recognises only B-AND/B-OR/B-XOR/B-NOT, not the four 2023 B-SHIFT-* operators, while the parser's boolExprAhead() predicate admits them -- a shift-only boolean expression routes to UnwrapBareBool, returns null, and is refused as a non-condition operand

**Repro.** 01 BW PIC 1 VALUE B"1". ... IF BW B-SHIFT-LC 1 DISPLAY "T1" ELSE DISPLAY "F1". IF BW B-SHIFT-L 1 DISPLAY "T2" ELSE DISPLAY "F2". IF BW B-SHIFT-L 1 = B"0" DISPLAY "T5" ELSE DISPLAY "F5". (cobol p2.cob --run, default --std 2023)

**Expected from the spec.** §8.8.2 lists 'a boolean expression and an integer operand separated by a boolean shift operator' as a boolean expression; §8.8.4.3.2 admits any boolean-expression-1 as a simple boolean condition; §8.8.2 rule 8: circular shift of a 1-position item leaves it 1, logical shift L of 1 yields 0. Expected output T1 / F2 / T5 at 2023 (and the COBOL-2023 introduction gate below 2023).

**Observed / reasoning.** error COBOLNET2318: 'operand' is used as a condition, but it is a literal, a figurative constant, a function reference or an arithmetic expression (lines 1-2 and `IF (BW B-SHIFT-RC 1)`); the relation sibling yields COBOLNET2362 'a IF statement was refused without a diagnostic naming the rule it breaks; this is a COBOL.NET internal error'. Cause read: ConditionBinder.cs HasBoolOp tests `term.Symbol.Type is Core.B_AND or Core.B_OR or Core.B_XOR or Core.B_NOT`; CobolParserCoreBase.boolExprAhead() fires on B_SHIFT_L/R/LC/RC too. The VersionConformancePass carries a deliberate HasBoolOp duplicate (line ~2394) -- sweep it for the same omission. BindBoolOrValueOperand (relation path) uses the same HasBoolOp.

**Code site.** src/Cobol.Net.Compiler/Binding/Procedure/Verbs/ConditionBinder.cs#HasBoolOp (line 311); callers BindPrimaryBoolean (line 278) and BindBoolOrValueOperand; src/Cobol.Net.Compiler/Validation/VersionConformancePass.cs#HasBoolOp (line 2394)
